Продолжаем держать вас в курсе событий. РКН научился определять VLESS XTL…

Продолжаем держать вас в курсе событий. РКН научился определять VLESS XTLS REALITY — вероятно, по косвенным признакам. Большинство VPN-сервисов, использовавших этот протокол, включая, конечно же, и нас, сейчас недоступны в ряде регионов либо работают крайне нестабильно. Речь идёт примерно о 90% таких сервисов. Наша команда определила несколько способов, которые РКН использует для борьбы с VPN-серверами. Основные из них: TCP DROP, DNS DROP, блокировка 16–20 и UDP SLOWDOWN. TCP DROP — полная блокировка TCP-трафика со стороны пользователя к серверу. Основной симптом такой блокировки — не устанавливается даже SSH-соединение, не работает MTR и, соответственно, отсутствуют ICMP-пинги. Разумеется, VPN при такой блокировке физически не способен подключиться. DNS DROP — новый и, пожалуй, наиболее распространённый сейчас тип блокировки. Вчера всё VPN-сообщество пыталось определить принципы её работы. Наконец нам и многим другим участникам сообщества — всем большое спасибо — удалось разобраться в её механизме. Пакеты, отправленные на 8.8.8.8, 1.1.1.1 и ряд других публичных резолверов, не покидают сеть провайдера, а перенаправляются на локальный DNS-кластер. Он отвечает с подменённым исходным IP-адресом, имитируя оригинальный резолвер. При совпадении с чёрным списком для A/AAAA-записей возвращается синтетический NXDOMAIN (AA=1), а при отсутствии данных в локальном кэше — REFERRAL на TLD из-за отключённой рекурсии (RA=0). TCP/53, DoT (853), DoH (443) и DNSCrypt не затрагиваются, поскольку фильтр срабатывает исключительно на UDP-пакеты, направленные на порт 53. При этом DNS-фильтрация не зависит от SNI/TLS-фильтрации. Даже если первую удаётся обойти с помощью шифрованного DNS, вторая по-прежнему может выполнять silent drop пакета ClientHello на основании SNI. Поэтому для доступа к некоторым ресурсам всё ещё необходим полноценный VPN или прокси. Блокировка 16–20 — старый тип блокировки. Её главный симптом: VPN приходится несколько раз включать и выключать, прежде чем он наконец заработает. Сейчас этот метод считается неэффективным, поскольку практически все VPN-провайдеры используют фрагментацию пакетов. UDP SLOWDOWN — на данный момент зафиксировано лишь несколько случаев применения этого метода. Массово он пока не используется. Теперь о нас. Мы закончили работу над собственным протоколом для наших приложений. Однако, к сожалению, именно сегодня компания Apple заблокировала все наши аккаунты Apple Developer. Несмотря на это, релиз протокола всё же состоится уже завтра или послезавтра в приложениях NashVPN для Windows, Android и Android TV. Версия для iOS пока выпущена не будет, поскольку наших приложений для iOS больше нет. Но это не причина печалиться. Это лишь небольшие трудности, за которые наша команда даже благодарна, ведь они делают нас сильнее.
